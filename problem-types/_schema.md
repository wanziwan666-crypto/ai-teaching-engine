# 题型骨架定义规范

> 每个题型一个 `.md` 文件。文件名即题型名。SETUP 阶段由 LLM 分类后查库读取。
> 骨架是**讲/练/总结三方共用的单一事实源**——一旦存入 state.json，三个环节强制读同一份，讲练脱节在架构上不可能发生。

## 文件结构（必填字段）

```markdown
# {题型名}

## 分类信号
- {识别这道题的关键词/句式，给 LLM 分类用，列 4-8 个}

## 适用范围
- {什么题目用这个骨架，什么题目不用；边界条件}

## 解题骨架
| 步 | 名称 | 核心点 | 练习类型 | 练习选项/提示 | 讲解红线 |
|----|------|--------|---------|-------------|---------|

- 步数：3-5 步。太多则拆题型，太少则说明这题不值得用骨架。
- 核心点：学生这一步必须自己想通的那个判断/运算。诊断时对照它判卡点。
- 练习类型：`choice`（判断型）或 `fill`（列式型）。
- 讲解红线：这一步铺垫绝不能剧透的东西（explain 反剧透规则的题型化锚点）。

## 题型特有注意点
- {该题型最容易踩的坑、特有的教学技巧，选填}

## 完成标记
- {讲完最后一步后，什么条件下输出 [[讲解完成]]。通常固定为"第N步确认理解后"}
```

## 命名

- 文件名用题型通用名：`相遇问题.md`、`鸡兔同笼.md`、`工程问题.md`
- 不加编号、不加学科前缀（题型库跨学科共用）

## 骨架写入 state.json 的格式

SETUP 读取 `.md` 后，转成结构化存入 state：

```json
{
  "skeleton": {
    "type": "相遇问题",
    "steps": [
      {"id":1, "name":"判断关系", "core_point":"...", "practice_type":"choice", "practice_options":["..."], "explain_constraint":"..."},
      ...
    ],
    "completion_rule": "讲完第4步确认理解后输出 [[讲解完成]]"
  }
}
```

之后 explain / practice / summarize 的 prompt **全部从 `state.skeleton.steps` 取步骤定义**，不再让 LLM 自己拆。

## 扩充规则

- 每次遇到库未覆盖的题，SETUP 走"LLM 生成骨架 → 学生/老师确认 → 可选回写进库"。
- 回写格式严格按本 schema，文件名取 LLM 判定的题型名。
- 回写前必须人工确认——错误骨架比没骨架更危险。
